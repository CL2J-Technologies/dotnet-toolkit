# Bulk insert

`BulkInsert` writes many rows with `SqlBulkCopy`. It is on the connection, not on `IDatabase`.

```cs
await using var connection = await database.CreateConnection();

var rows = Enumerable.Range(0, 100_000)
    .Select(i => new Reading { Sensor = "s" + (i % 10), Value = i })
    .ToList();                                  // materialise the list first

await connection.BulkInsert(rows);
```

## Speed

From [`benchmarks/README.md`](../../benchmarks/README.md), 1,000,000 rows into SQL Server:

| | Time |
|---|---|
| cl2j.Database `BulkInsert` | 1.53 s |
| Hand-written `SqlBulkCopy` | 1.48 s |
| EF Core | 34.4 s |

Dapper has no bulk API of its own (Dapper Plus is a commercial add-on), so there is no like-for-like Dapper
row. The benchmark used `Connection Timeout=300`.

## Keys

The same key rules as [`Insert`](insert-update-delete.md#insert):

- `int`, `long` and `Guid` `KeyType.Key` columns are **left out**; the server fills them in. They are not
  returned: a bulk insert gives you no identities.
- A `string` `Key` is sent as is.
- `AutoGeneratedKey` values are generated for every row (and **overwrite** any value you set), then written to
  the entities you passed.

## Materialise your sequence

**Pass a `List<T>` or an array, not a lazy `IEnumerable<T>`**, when the entity has an
`AutoGeneratedKey`. The keys are generated in one pass over the sequence and the rows are read again in a
second pass. A lazy sequence such as `Enumerable.Range(...).Select(i => new T { ... })` creates new objects on
each pass, so the second pass sees objects without keys and the insert fails with a duplicate-key error. For a
sequence with no generated keys a lazy `IEnumerable` is fine.

This is a defect (the two passes are in `ConnectionExtensions.BulkInsert`); the workaround is `.ToList()`.

## Timeout

The timeout is read from the **static** `ConnectionExtensions.DatabaseOptions` (set by
`host.UseDatabase()`), not from the `DatabaseOptions` instance given to `SqlServerDatabase`:

| `BulkInsertTimeout` | Timeout used |
|---|---|
| a value | that value, rounded up to whole seconds |
| not set | the connection's `Connection Timeout` |
| `TimeSpan.Zero` | unlimited |

(`BulkInsertTimeoutTests`.)

## What it is not

- It is **in memory**: the rows are copied into a `DataTable` first, so the whole batch has to fit in
  memory. Split a very large source into chunks of, say, 100,000 rows.
- It uses `SqlBulkCopyOptions.Default`: `SqlBulkCopy` does not fire triggers or check constraints in that mode
  (Microsoft's documented behaviour; it is not covered by a test here).
- It can take a `CancellationToken` and a `DbTransaction`; see [Transactions](transactions.md). A bulk insert
  inside a transaction that is rolled back leaves nothing behind (**observed**; no repository test).
- Nothing is returned, and a failure part-way is not rolled back unless you use a transaction.
- Null values are written as SQL `NULL`, including a JSON column (`Insert` writes the text `null` there; both
  read back as `null`). See [JSON columns](json-columns.md).
